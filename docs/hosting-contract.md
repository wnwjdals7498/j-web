# H2 호스팅 하위 계약

2026-10-09. 사이트 설치와 독립 콘텐츠/readonly preview 계약이다. 내부 j-web API이며 정식 화면은 별도 구현이다. 모든 변경은 실제 j-web 단일 aud 회원 Bearer와 `web:write`, 조회는 `web:read`를 요구한다. 브라우저 cookie를 직접 받지 않는다.

| 경로                                   | 입력과 결과                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| POST `/web/sites`                      | `{domain,password?}` → 201 `{id,domain,state:active,account,password}`. 암호 생략 시 난수 생성. 도메인 충돌 409.                                                                                                                                                                                                                     |
| GET `/web/sites/:id/hosting`           | 상태·계정·실제 단계/오류·du bytes·데이터 디스크 bytes·HTTPS origin·SFTP/FTPS 포트·DNS A 안내. 암호 없음. 고객 IPv4 미설정이면 안내 address는 null. 실제 DNS 변경 호출 없음.                                                                                                                                                          |
| POST `/web/sites/:id/deploy`           | `{expectedRevision}` → `{siteId,revision,origin,deployed,previousVersion}`. 현재 저장 revision만 배포하고 origin은 `https://<site.domain>`이다. 같은 revision 재요청은 live index SHA-256이 비공개 helper manifest와 같을 때 `deployed:false`로 멱등 성공한다. `previousVersion`은 내부 경로가 아닌 불투명 UUID며, 첫 배포는 `null`. |
| POST `/web/sites/:id/retry`            | `{password?}` → 동일 id의 실패한 생성 작업 재시도·새 암호 1회. active·삭제 중·관리하지 않는 기존 행은 409.                                                                                                                                                                                                                           |
| POST `/web/sites/:id/account-password` | `{password?}` → `{id,account,password}`. 실제 OS 암호 교체 후 200.                                                                                                                                                                                                                                                                   |
| DELETE `/web/sites/:id`                | 실제 helper 블록·계정 제거·파일 백업 뒤 `{id,backupId}`. 성공 전 DB 행 삭제 없음.                                                                                                                                                                                                                                                    |

별도 마운트 확인 뒤 DB에 생성 의도를 먼저 기록한다. helper 실패는 503 `{code,message,requestId,siteId,phase}`이며 같은 id를 보존한다. DB의 단계는 `site_create/account_create/nginx_apply/active/delete`, 상태는 기존 creating/active/deleting/failed다. 암호나 stdout/stderr를 DB·로그·오류에 저장하지 않는다. DB 연결의 사이트별 advisory lock은 여러 프로세스의 같은 사이트 변경을 직렬화한다. helper 잠금은 실제 OS 작업을 한 번에 하나만 허용한다.

배포 helper는 요청 UUID·revision·제한된 HTML을 재검증한다. 첫 `index.html`이 이미 있거나, 관리 배포된 파일의 현재 바이트가 private root-owned SHA-256 manifest와 다르면 409 `template_conflict`다. 배포는 managed `index.html` 하나만 atomic rename으로 바꾸고, SFTP/FTPS의 다른 파일은 삭제·이름변경하지 않는다. 바꾸기 직전의 관리 바이트는 root-only private backup에 저장하고, private journal로 파일 교체와 상태 기록 사이의 중단을 복구한다. 실제 owned hosting fixture는 backup 생성 전 journal과 atomic 교체 후 미확정 journal을 각각 재시도해 복구를 검증한다. helper 사이트 잠금은 privileged helper 작업만 직렬화하며 SFTP/FTPS writer는 이 잠금에 참여하지 않는다. helper는 atomic rename 직전에 index drift를 다시 확인하지만, 외부 업로드와 그 짧은 확인·rename 구간의 동시 경쟁을 완전히 직렬화하지는 않는다. 현재 page·helper path가 symlink, owner 불일치 또는 중첩 mount면 쓰기를 거절한다. 실제 운영 OS의 Nginx 설치/변경은 이 구현 검증 범위가 아니다.

도메인은 소문자 RFC1123·고정 접미사, 계정명은 UUID에서 계산한 `jw-` 이름이다. API는 임의 계정·tenant·경로·Nginx 설정을 받지 않는다. 다른 tenant/없는 id는 쓰기에도 404다. contracts 0.1.0은 최초 loopback registry에 게시하고 exact consumer/integrity를 확인했다. [콘텐츠 입력·미리보기·DNS 계약과 검증](cloud-content-contract-verification-2026-10-09.md)을 따른다. H7 정책은 관리 template의 `index.html`에만 atomic 배포를 허용하고, unmanaged·드리프트 파일은 409로 거절하며 다른 수동 파일은 보존한다.
